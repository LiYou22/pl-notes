\section{Names: \texttt{let} and Substitution}
\label{sec:letsubst}

\subsection{The Plan}

At the end of \Cref{ch:week3}, the calculator had three forms: \code{numC}, \code{plusC}, and \code{timesC}. This section adds names, through a new form \code{(let x e1 e2)}. It means: compute \code{e1}, replace every \code{x} in \code{e2} with the result, and then compute \code{e2}.
\begin{lstlisting}[style=repl]
(let x 5 (+ x x))
---> (+ 5 5)                 replace every x in the body with 5
---> 10

(let x (+ 1 5) (+ x x))
---> (let x 6 (+ x x))       e1 is evaluated first
---> (+ 6 6)
---> 12
\end{lstlisting}

\subsection{Two New Variants}

\begin{lstlisting}
(define-type ArithE
  [numC (n : number)]
  [idC (x : symbol)]
  [plusC (e1 : ArithE) (e2 : ArithE)]
  [timesC (e1 : ArithE) (e2 : ArithE)]
  [letC (x : symbol) (e1 : ArithE) (e2 : ArithE)])
\end{lstlisting}
\Cref{sec:lambda} will add two more variants for functions, and from then on every function on \tyname{ArithE} needs a case for them.

\subsubsection{What is \code{idC} for?} An \code{idC} represents a \emph{use} of a name, such as the \code{x} in \code{(+ x 1)}. We need it because of types. The operands of \code{plusC} must be \tyname{ArithE}s, and a bare symbol like \code{'x} is not one. Wrapping the symbol in \code{idC} turns it into an \tyname{ArithE}, so the name can sit in the tree until substitution replaces it. In this sense, \code{idC} does for symbols what \code{numC} does for numbers.

A name can appear in two roles, and only one of them becomes an \code{idC}:
\begin{lstlisting}
;; (let x 5 (+ x 1))
(letC 'x (numC 5) (plusC (idC 'x) (numC 1)))
;;    ^ binding: a plain symbol    ^ use: an idC
\end{lstlisting}
The name right after \code{let} is the one being \emph{bound}. It is stored as a plain symbol in \code{letC}, because it is never evaluated or replaced. Its only job is to tell substitution which name to look for.

Keywords like \code{+} and \code{let} never become \code{idC}s either, because \code{parse} uses them up when it decides which variant to build. Note also that \rkt|(plusC 'x (numC 1))| is a type error: \code{'x} is a \tyname{symbol}, not an \tyname{ArithE}.

\subsubsection{Parsing} A lone symbol becomes an \code{idC}. In \code{(let x e1 e2)}, the \code{x} is kept as a plain symbol, and \code{e1} and \code{e2} are parsed recursively:
\begin{lstlisting}
(define (parse (s : s-expression)) : ArithE
  (cond
    [(s-exp-number? s) (numC (s-exp->number s))]
    [(s-exp-symbol? s) (idC (s-exp->symbol s))]
    [(s-exp-list? s)
     (let [(l (s-exp->list s))]
       (case (s-exp->symbol (first l))
         [(+) (plusC (parse (second l)) (parse (third l)))]
         [(*) (timesC (parse (second l)) (parse (third l)))]
         [(let) (letC (s-exp->symbol (second l)) (parse (third l)) (parse (fourth l)))]))]))
\end{lstlisting}
As in \Cref{sec:calc}, this parser does no error checking. For example, \rkt|(parse '(let x 1))| fails inside \code{fourth}, with the message \code{list contains too few elements}.

\subsection{Eager Substitution}

\rkt|(subst-eager v x e)| replaces every \code{x} in \code{e} with the number \code{v}. Most cases simply recurse into the children. The interesting cases are the two that involve names, \code{idC} and \code{letC}.
\begin{lstlisting}
(define (subst-eager (v : number) (x : symbol) (e : ArithE)) : ArithE
  (type-case ArithE e
    [numC (n) (numC n)]
    [idC (y) (if (equal? x y) (numC v) (idC y))]
    [plusC (e1 e2) (plusC (subst-eager v x e1) (subst-eager v x e2))]
    [timesC (e1 e2) (timesC (subst-eager v x e1) (subst-eager v x e2))]
    [letC (y e1 e2)
          (letC y
                (subst-eager v x e1)
                (if (equal? x y) e2 (subst-eager v x e2)))]))
\end{lstlisting}

\subsubsection{Why \code{(numC v)} and \code{(idC y)}?} \code{subst-eager} must return an \tyname{ArithE}, but \code{v} is a number. So when it finds the name, it wraps \code{v} as \rkt|(numC v)| before putting it back into the tree. When it finds a different name, it leaves that name alone: \rkt|(idC y)| rebuilds the same node, which is the same as returning \code{e}.
\begin{lstlisting}
(subst-eager 5 'x (plusC (idC 'x) (idC 'y)))   ; = (plusC (numC 5) (idC 'y))
\end{lstlisting}

\subsection{Shadowing}

What is \code{(let x 5 (let x 6 (+ x x)))}: 12 or 10? The answer is 12. The inner \code{let} binds its own \code{x}, so inside its body, \code{x} means 6. We say the inner \code{x} \emph{shadows} the outer one (\Cref{fig:shadow}).

\begin{figure}[htbp]
\centering
\begin{tikzpicture}[tok/.style={inner sep=0pt, font=\ttfamily\normalsize, anchor=base west}]
  \node[tok] at (0,0) {(let x 5 (let x 6 (+ x x)))};
  \node[tok] (x1) at (5\cw,0) {\phantom{x}};
  \node[tok] (x2) at (14\cw,0) {\phantom{x}};
  \node[tok] (u1) at (21\cw,0) {\phantom{x}};
  \node[tok] (u2) at (23\cw,0) {\phantom{x}};
  \draw[bind] (u1.south) to[out=-110, in=-70] (x2.south);
  \draw[bind] (u2.south) to[out=-110, in=-70] (x2.south);
  \node[lbl, below=8mm of u1, text=accent] {both uses refer to the inner binder};
  \node[lbl, above=1mm of x1] {outer};
  \node[lbl, above=1mm of x2] {inner};
\end{tikzpicture}
\caption{Each use of a name refers to the nearest enclosing binder of that name.}
\label{fig:shadow}
\end{figure}

This is what the \rkt|(equal? x y)| check in the \code{letC} case is for. If an inner \code{let} binds the same name we are substituting for, substitution does not go into that \code{let}'s body.
\begin{lstlisting}[style=repl]
(let x 5 (let x 6 (+ x x)))
---> (let x 6 (+ x x))       the outer subst leaves the inner body alone
---> (+ 6 6)
---> 12
\end{lstlisting}
Without the check, substitution would produce \code{(let x 6 (+ 5 5))}, which is 10.

The check only protects the inner \emph{body}. The inner \code{e1} is still substituted, because it lies \emph{outside} the inner binding: the inner \code{x} is visible only in the inner body.
\begin{lstlisting}[style=repl]
(let x 1 (let x (+ x 1) x))
---> (let x (+ 1 1) x)       the x in e1 is the outer x
---> 2
\end{lstlisting}

\subsection{\texttt{eval-eager}}

\begin{lstlisting}
(define (eval-eager (e : ArithE)) : number
  (type-case ArithE e
    [numC (n) n]
    [idC (x) (error 'eval "unbound variable")]
    [plusC (e1 e2) (+ (eval-eager e1) (eval-eager e2))]
    [timesC (e1 e2) (* (eval-eager e1) (eval-eager e2))]
    [letC (y e1 e2) (eval-eager (subst-eager (eval-eager e1) y e2))]))
\end{lstlisting}
The \code{letC} line follows the plan exactly: evaluate \code{e1}, substitute the resulting number for \code{y} in \code{e2}, and evaluate what comes out.

Why is the \code{idC} case an error? If a name is bound by some \code{let}, that \code{let} substitutes it away before \code{eval-eager} ever reaches it. So any \code{idC} that \code{eval-eager} does see was never bound, as in \code{(+ x 1)}, and that is an error.
\begin{lstlisting}[style=repl]
(let x 5 (let y (+ x 1) (* x y)))
letC x: eval e1 = 5, subst 5 for x in the body
---> (let y (+ 5 1) (* 5 y))
letC y: eval e1 = 6, subst 6 for y in the body
---> (* 5 6)
---> 30
\end{lstlisting}
Each \code{let} removes the \code{idC}s for its own name. Once every \code{let} has been processed, no \code{idC} is left.
