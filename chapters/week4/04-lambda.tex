\section{Functions: \texttt{lambda} and Application}
\label{sec:lambda}

\subsection{Syntax}

This section adds functions to the language, through two new forms:
\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
syntax & meaning & abstract syntax \\
\midrule
\code{(lambda x e)} & a function with parameter \code{x} and body \code{e} & \code{lambdaC} \\
\code{(e1 e2)} & call the function \code{e1} on the argument \code{e2} & \code{appC} \\
\bottomrule
\end{tabular}
\end{center}
\begin{lstlisting}
(define-type ArithE
  [numC (n : number)]
  [idC (x : symbol)]
  [plusC (e1 : ArithE) (e2 : ArithE)]
  [timesC (e1 : ArithE) (e2 : ArithE)]
  [letC (x : symbol) (e1 : ArithE) (e2 : ArithE)]
  [lambdaC (x : symbol) (e : ArithE)]
  [appC (e1 : ArithE) (e2 : ArithE)])
\end{lstlisting}
\code{lambdaC} \emph{defines} a function, and \code{appC} \emph{uses} one. The pair works much like \code{letC} and \code{idC}: one introduces a name, the other uses it. Every function takes exactly one argument. Several arguments can be simulated by currying (\Cref{sec:hof}).

\subsubsection{Parsing} A list whose head is not \code{+}, \code{*}, \code{let}, or \code{lambda} is an application:
\begin{lstlisting}
(define (parse (s : s-expression)) : ArithE
  (cond
    [(s-exp-number? s) (numC (s-exp->number s))]
    [(s-exp-symbol? s) (idC (s-exp->symbol s))]
    [(s-exp-list? s)
     (let [(l (s-exp->list s))]
       (if (s-exp-symbol? (first l))
           (case (s-exp->symbol (first l))
             [(+) (plusC (parse (second l)) (parse (third l)))]
             [(*) (timesC (parse (second l)) (parse (third l)))]
             [(let) (letC (s-exp->symbol (second l)) (parse (third l)) (parse (fourth l)))]
             [(lambda) (lambdaC (s-exp->symbol (second l)) (parse (third l)))]
             [else (appC (parse (first l)) (parse (second l)))])
           ;; head is not a symbol, e.g. ((lambda x (+ x 1)) 5)
           (appC (parse (first l)) (parse (second l)))))]))
\end{lstlisting}
\begin{lstlisting}
(parse '((lambda x (+ x 1)) 5))
;; = (appC (lambdaC 'x (plusC (idC 'x) (numC 1))) (numC 5))
(parse '(f 5))
;; = (appC (idC 'f) (numC 5))
\end{lstlisting}
The outer \code{if} handles calls whose head is itself a list, such as \code{((lambda x (+ x 1)) 5)}. Without it, \code{parse} would call \code{s-exp->symbol} on that list and fail with \code{s-exp->symbol: not a symbol}.

\begin{remark}
Because applications are the fallback, \code{'(- 1 2)} no longer fails to parse. The \code{else} branch reads it as a call of a function named \code{-}. The result is \rkt|(appC (idC '-) (numC 1))|, and the \code{2} is silently dropped. Before \code{lambda} was added, the same input failed with \code{case: no matching clause}.
\end{remark}

\subsection{\texttt{lambda} in Substitution}

A \code{lambda} binds its parameter in its body, exactly as \code{let} binds \code{x} in \code{e2}. So the \code{lambdaC} case of each substitution function is its \code{letC} case without an \code{e1}. It stops at shadowing, and in \code{subst-lazy-v2} it first renames the parameter with \code{gensym}. The application case simply recurses.
\begin{lstlisting}
;; in subst-eager (subst-lazy is the same with subst-lazy)
[lambdaC (y e)
         (if (equal? x y) (lambdaC y e) (lambdaC y (subst-eager v x e)))]
[appC (e1 e2) (appC (subst-eager v x e1) (subst-eager v x e2))]

;; in subst-lazy-v2
[lambdaC (y e)
         (if (equal? x y)
             (lambdaC y e)
             (let [(z (gensym))]
               (lambdaC z (subst-lazy-v2 v x (subst-lazy (idC z) y e)))))]
[appC (e1 e2) (appC (subst-lazy-v2 v x e1) (subst-lazy-v2 v x e2))]
\end{lstlisting}

\begin{pitfall}[The pattern variable shadows the argument]
In \rkt|[lambdaC (y e) ...]|, the pattern variable \code{e} is the body. It shadows \code{subst}'s own argument \code{e}, which is the whole \code{lambda}. So the shadowing branch must rebuild \rkt|(lambdaC y e)|. Returning plain \code{e} would drop the \code{lambda} and return only its body. Shadowing bites the interpreter's author too.
\end{pitfall}

\subsection{A New Result Type}

A program can now produce a function, for example \code{(lambda x (+ x 1))} or \code{(let f (lambda x x) f)}. A function is not a number, so evaluation must return a more general type. That type is \tyname{Value}, which is one of two things:
\begin{lstlisting}
(define-type Value
  [numV (n : number)]
  [funV (x : symbol) (e : ArithE)])
\end{lstlisting}
\code{+} and \code{*} only make sense on numbers. So they first check that both operands are \code{numV}s, unwrap them, and report an error for anything else:
\begin{lstlisting}
(define (num+ (v1 : Value) (v2 : Value)) : Value
  (if (and (numV? v1) (numV? v2))
      (numV (+ (numV-n v1) (numV-n v2)))
      (error 'eval "not a number")))

(define (num* (v1 : Value) (v2 : Value)) : Value
  (if (and (numV? v1) (numV? v2))
      (numV (* (numV-n v1) (numV-n v2)))
      (error 'eval "not a number")))
\end{lstlisting}
This is the first \emph{dynamic} type error in our language. Whether \code{(+ e1 e2)} makes sense depends on what \code{e1} and \code{e2} evaluate to, and the interpreter only learns that at run time.

\subsection{Eager Application}
\label{sec:eagerapp}

We first add functions to the \emph{eager} interpreter. Here application is \emph{call-by-value}: evaluate the function, evaluate the argument, and then substitute the argument's \emph{value} into the body. \code{let} works the same way.

There is one obstacle. \code{subst-eager} can only substitute numbers, but a value may now be a function. So the interpreter turns the value back into an expression, and substitutes it with \code{subst-lazy} or \code{subst-lazy-v2}, which substitute expressions. Nothing about this is lazy, because the expression they receive has already been evaluated:
\begin{lstlisting}
(define (value->expr (v : Value)) : ArithE
  (type-case Value v
    [numV (n) (numC n)]
    [funV (x e) (lambdaC x e)]))

(define (eval-eager-v2 (e : ArithE)) : Value
  (type-case ArithE e
    [numC (n) (numV n)]
    [idC (x) (error 'eval "unbound variable")]
    [plusC (e1 e2) (num+ (eval-eager-v2 e1) (eval-eager-v2 e2))]
    [timesC (e1 e2) (num* (eval-eager-v2 e1) (eval-eager-v2 e2))]
    [letC (y e1 e2)
          (eval-eager-v2 (subst-lazy (value->expr (eval-eager-v2 e1)) y e2))]
    [lambdaC (x e) (funV x e)]
    [appC (e1 e2)
          (type-case Value (eval-eager-v2 e1)
            [funV (x e)
                  (eval-eager-v2 (subst-lazy (value->expr (eval-eager-v2 e2)) x e))]
            [numV (n) (error 'eval "not a function")])]))
\end{lstlisting}
The accompanying code, \code{lec4d.rkt}, uses different names: it writes \code{Expr} for \tyname{ArithE} and \code{lambdaV} for \code{funV}. It also passes \code{subst} a \tyname{Value} and converts it at the \code{idC} case. The effect is the same.

With this, functions can be passed around:
\begin{lstlisting}[style=repl]
(let do-twice (lambda f (f (f 1)))
  (let double (lambda x (* 2 x))
    (do-twice double)))
---> (do-twice double)  with both substituted
---> (double (double 1))
---> 4
\end{lstlisting}

\subsubsection{Eager capture} \Cref{sec:lazy} argued that eager substitution cannot capture, because a number contains no names. A function value, however, does contain names, and its body may contain free variables:
\begin{lstlisting}[style=repl]
(let f (lambda x (+ x y))         y is free in f's body
  (let y 6
    (f 1)))
---> (let y 6 ((lambda x (+ x y)) 1))   substitute f's value: y is captured
---> ((lambda x (+ x 6)) 1)
---> 7
\end{lstlisting}
The right answer is an error. The \code{y} in \code{f} refers to no binding, and Racket rejects the same program with \code{y: unbound identifier}. \code{eval-eager-v2} returns 7 because \code{subst-lazy} carried the free \code{y} under \code{(let y 6 ...)}. So once values can contain code, eager evaluation no longer protects against capture.

The fix is the same as in \Cref{sec:capavoid}. \code{eval-eager-v3} is \code{eval-eager-v2} with both calls to \code{subst-lazy} replaced by \code{subst-lazy-v2}. Now the program above raises \code{unbound variable}. Returning \code{f} instead of calling it shows the renaming:
\begin{lstlisting}[style=repl]
> (eval-eager-v3 (parse '(let f (lambda x (+ x y)) (let y 6 f))))
(funV 'g3507 (plusC (idC 'g3507) (idC 'y)))
\end{lstlisting}
When \code{f} was substituted into the body of \code{(let y 6 ...)}, its parameter was renamed to a fresh name. The \code{lambdaC} case of \code{subst-lazy-v2} always does this. The free \code{y} stays free.

\subsection{Lazy Application: \texttt{eval-lazy-v2}}

The last version makes application lazy, just like \code{let} in \Cref{sec:lazy}. The argument is substituted without being evaluated.

\begin{lstlisting}
(define (eval-lazy-v2 (e : ArithE)) : Value
  (type-case ArithE e
    [numC (n) (numV n)]
    [idC (x) (error 'eval "unbound variable")]
    [plusC (e1 e2) (num+ (eval-lazy-v2 e1) (eval-lazy-v2 e2))]
    [timesC (e1 e2) (num* (eval-lazy-v2 e1) (eval-lazy-v2 e2))]
    [letC (y e1 e2) (eval-lazy-v2 (subst-lazy-v2 e1 y e2))]
    [lambdaC (x e) (funV x e)]
    [appC (e1 e2)
          (type-case Value (eval-lazy-v2 e1)
            [funV (x e) (eval-lazy-v2 (subst-lazy-v2 e2 x e))]
            [numV (n) (error 'eval "not a function")])]))
\end{lstlisting}
\begin{itemize}
  \item \textbf{\code{lambdaC}}: a \code{lambda} is already a value. Nothing needs to be computed until it is called.
  \item \textbf{\code{appC}}: first evaluate \code{e1}, which must give a function \rkt|(funV x e)|. Then call it the way \code{let} works: substitute the argument \code{e2} for \code{x} in the body \code{e}, and evaluate the result. Since this is the lazy version, \code{e2} is substituted unevaluated.
\end{itemize}
\begin{lstlisting}[style=repl]
((lambda x (+ x 1)) 5)
---> (+ 5 1)             subst 5 for x in the body
---> 6
\end{lstlisting}

\begin{keypoint}[\code{let} is application]
\code{((lambda x e) e2)} means the same as \code{(let x e2 e)}. What \code{lambda} adds is that the function is a \emph{value}. It can be named with \code{let}, passed as an argument, and returned as a result.
\end{keypoint}

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
program & result \\
\midrule
\code{(let f (lambda x (* x 2)) (f 5))} & \code{(numV 10)} \\
\code{((lambda f (f 3)) (lambda x (+ x 1)))} & \code{(numV 4)}: a function as argument \\
\code{(((lambda x (lambda y (+ x y))) 1) 2)} & \code{(numV 3)}: a function as result \\
\code{((lambda x 5) y)} & \code{(numV 5)}: the unused argument is never evaluated \\
the \code{do-twice} example of \Cref{sec:eagerapp} & \code{(numV 4)} \\
\code{(5 3)} & \code{not a function} \\
\code{(+ (lambda x x) 1)} & \code{not a number} \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Capture, Again}

With functions, capture-avoiding substitution matters even more. A function can return a function, so a free name can end up under another \code{lambda}:
\begin{lstlisting}[style=repl]
(((lambda x (lambda y (+ x y))) y) 2)
subst-lazy:     (lambda y (+ y y)),  then 2 ---> 4          captured!
subst-lazy-v2:  (lambda g (+ y g)),  then 2 ---> (+ y 2) ---> unbound variable
\end{lstlisting}
The earlier interpreters \code{eval-eager} and \code{eval-lazy} still return a \code{number}, and \code{subst-eager} can only substitute numbers. So their \code{lambdaC} and \code{appC} cases remain errors (\code{"TODO: lambda"}). The versions that support functions are \code{eval-eager-v2}/\code{v3} and \code{eval-lazy-v2}.

\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
program & \code{eval-eager-v3} (call-by-value) & \code{eval-lazy-v2} (call-by-name) \\
\midrule
\code{((lambda x 5) y)} & \code{unbound variable} & \code{(numV 5)} \\
\code{(let x (+ y y) 10)} & \code{unbound variable} & \code{(numV 10)} \\
the \code{f}/\code{y} example of \Cref{sec:eagerapp} & \code{unbound variable} & \code{unbound variable} \\
\bottomrule
\end{tabular}
\end{center}
With capture-avoiding substitution, the two strategies differ only when an argument is never used, just as for \code{let} in \Cref{sec:lazy}. Racket, like most languages, is call-by-value.
